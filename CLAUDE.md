# Claude Code — project instructions

An agent-native job-search toolkit, driven through the **`jobstudio`** skill
(`/jobstudio help` for the subcommand list). This file loads automatically in every
session; it's a map, not a manual — read the file it points to rather than expecting the
answer here.

## The one thing to get right

**Code and data are separate directories.** This repo is the toolkit. The user's job
search — CVs, applications, company research, the database — lives in a **data root**
outside it, and nothing personal is ever committed here.

Every data path in the skill is written `<DATA>/...`. Resolve it once per subcommand
that touches a file:

1. `tools/py src/config.py --path` when the repo is reachable — it applies the full
   layering (`$JOBSTUDIO_DATA`, then `.jobstudio-data`, then `~/.jobstudio.ini`)
2. `~/.jobstudio.ini` directly when it is not — the working directory is often the data
   root rather than the repo
3. Otherwise stop and say to run `/jobstudio init`. Never guess, and never fall back
   to the current directory.

A bare `jobs/...` path resolves against the working directory, so a write can silently
land **in this repo** instead of the user's data. That is the failure the convention
exists to prevent.

**Working on the toolkit is not the same as using it.** A bare command here resolves to
whatever `~/.jobstudio.ini` names — on a maintainer's machine that is their *real* job
search, not test data. So when changing code that writes files, point it somewhere
throwaway first:

```bash
JOBSTUDIO_DATA=/path/to/scratch-data tools/py src/...
```

The test suite pins itself to `example-data/` regardless (`settings.py` sets the env var
before `local_settings` is imported), and `smoke-test` works in a temp clone — so both
are safe to run as-is. It is ad-hoc script runs that are not.

## Where things are

| Question | Look here |
|---|---|
| How do I do X? (log an application, tailor a CV, run a scan…) | `/jobstudio help`, then `.claude/skills/jobstudio/subcommands/<name>.md` |
| How does a piece work internally? | `docs/README.md` — start at `docs/workflow.md`, then its linked deep-dives |
| Repo layout, setup | `README.md` |
| What's planned but not built? | `backlog/TODO.md` — numbered, permanent IDs; plan docs alongside it in `backlog/` |
| Why was a past decision made? | `log/*.md` — dated, append-only session records, richer than a changelog |
| What shipped, and when? | `CHANGELOG.md` — dated entries, newest first |

## Python

- **Never use `source` or `workon`** — unreliable, and they trigger permission prompts.
- **Always go through the wrapper:** `tools/py <script>`. It `exec`s the virtualenv's
  interpreter, so this is the same as naming the binary without baking a machine-specific
  path into every file. It is generated by `/jobstudio init` and gitignored. If it is
  missing, run `init`, or set `$JOBSEARCH_PY`.

## Checks

```bash
tools/py src/web/manage.py test tracker cvs   # test suite — runs against example-data/
tools/smoke-test                              # from-scratch install in a temp clone
tools/make-public-tree --check                # nothing personal about to be published
```

All three should pass before anything is considered done. `smoke-test` is the one that
catches assumptions only visible to someone who does not already have the files.

`--check` is the one that matters when you have written prose. **This repo is public and
pushes `dev` as well as `main`, so every push publishes** — and a changelog entry, a
TODO, a docstring or a test fixture is where a real company name from the user's own
search ends up. It has caught exactly that more than once. A `pre-push` hook runs it, but
run it yourself rather than discovering a leak at push time: use `example-data/`
(`001-grafana-labs`, `alex-rivera`) for every worked example, never a real application.
