- [x] `#65` **Restoring a backup invented status history, and reset every application's "last moved" to the restore date** — found and fixed 2026-10-01 while doing `#64`. `_application_saved` had no `raw` guard, and `loaddata` saves an `Application` *before* its `ApplicationStatusChange` rows — so the log looked empty, `_log_status_change` dutifully appended a `(logged) → <current status>` row stamped at load time, and the real rows then loaded underneath it. The example's dump held 25 changes and loading it produced 28.

  **It is not an example-data problem.** The damage is to anyone restoring a backup, and it is quiet: the invented row is the *most recent* change, so `_ageing_at_applied` reads every restored application as having moved today and **the staleness flagging silently stops working** — which is the one feature whose whole job is to tell you what you have forgotten. The stock chart also gets a cluster of same-second changes that `is_organic` reads as a bulk logging session, and the Sankey grows entry stubs for transitions nobody made. Nothing errors; the history is simply wrong, in the direction of looking healthier than it is.

  Fixed with the guard Django provides for exactly this (`raw=True` means a fixture load, where the row is being restored field-for-field and no transition is happening). `refresh_company_status` is skipped on the same branch, since on a restore the company's status came out of the dump where it had already been derived. A test asserts the loaded database holds exactly the change rows the dump file holds — compared against the file rather than a fixed number, because the number will keep changing — and it fails with `31 != 27` if the guard is removed.

  Worth noting how it surfaced: not from a test, but from one chart reporting an application as 0 days old when its last recorded change was 16 days earlier. The arithmetic was right and the data underneath it was wrong, which is the class of bug `--check` was built for in `#44` and the same class `#61` turned out to be.

- [x] `#41` **`jobsdb.py update-company`** — raised 2026-09-27 as optional, retitled and **built 2026-10-01** once the second-person install pass hit it within the hour. Creating a company had a CLI; changing one did not, so editing a `role_target`, `fit`, `category`, `url` or `notes` meant the Django admin or a `manage.py shell -c` one-liner. Fine for a person — the admin is the editing surface by design — and wrong for an agent, which is how every other tracker write happens.

  Two independent demands behind it in the end. The original: one change of direction re-pointed three fields across two companies as three shell calls, and a pivot across twenty rows would have been unbearable. The second: a new user found two tracked careers URLs gone stale (a 404 and a redirect to an acquirer) and had no command to correct either — their session's own conclusion was "you'll need to do it in the web admin".

  Built to the shape the entry specified, with three decisions worth keeping:

  - **Only the flags given are touched**, and a sentinel default rather than `None`, because `""` is a meaningful value here — `--url ""` is how a stale careers URL gets cleared, which is the case that prompted it. A command that reset the fields it was not given would be worse than no command, since the loss would be invisible.
  - **An ambiguous name prefix is refused**, not resolved to the lowest `num`. This is deliberately stricter than `find_application`, which does resolve a prefix: a read can afford that guess and a write cannot, and being asked to be specific beats editing the wrong company silently.
  - **No `--name`**, as specified. The slug derives from the name, and the company page URL plus the `company_overrides`, `company_areas` and `known_unsupported` keys in `scan-config.yaml` are keyed on name or slug — renaming through this command would quietly break scan coverage for that company. Still open as its own job, with those call sites to update; `docs/under-the-hood.md` now says so rather than claiming no edit command exists.

  `--category` reuses `add-company`'s `_resolve_category`, so an unknown name is refused the same way rather than this command inventing a laxer rule. Five tests, including that an unpassed field is untouched and that the ambiguous-prefix refusal fires. Documented in `subcommands/company.md` (with an explicit "do not send the user to the Django admin"), `docs/companies.md` and `docs/under-the-hood.md`.
